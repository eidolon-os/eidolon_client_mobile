# 主机切换后偶发连接失败分析

诊断基线：`6cb065d`。下文先记录原有行为及证据，修复实施情况见文末。

## 结论与证据

平板现有日志中有一段与用户描述吻合的记录：

| 时间（2026-09-10，本地时间） | 目标 | 结果 |
| --- | --- | --- |
| 16:16:40.769 | RK3588 / orangepi5-max | mDNS 已解析为 `192.168.1.33:9002` |
| 16:16:54.033 | `192.168.1.33:9002` | TCP connect 约 8011 ms 后 `SocketTimeoutException`；原生超时配置为 8000 ms |
| 16:17:08.064 | 同一地址、同一 TLS 指纹目标 | 请求约 118 ms 成功，后续认证及资料请求继续成功 |

第一次失败发生于 TCP 建连阶段，尚未到 TLS、管理授权或 Workspace 读取。该请求原生日志明确为 `SocketTimeoutException`，而不是页面关闭引起的 `cancelled`。因此目前证据支持“目标地址短暂无法建立 TCP 连接”，不能仅根据来回切换的操作顺序归因于页面状态串台。

这些日志不能区分当时的 Wi-Fi 链路、主机网络/监听状态或瞬时负载。若继续追查底层原因，需要故障时主机侧日志或双端抓包，正常恢复后的读数无法证明过去发生了什么。

## 客户端确认的行为

1. 首次连接缺少对短暂传输故障的有限恢复。`HostProductSession._connectCurrentNetwork` 只在网络 revision 改变时重新连接；网络标识不变的超时直接抛出。`HostLocator.locate` 对同一轮候选 URL 去重，已发现的地址超时后，相同的已保存地址不会再试一次。原生 HTTP 的自动重试也明确关闭。因此一次短暂 TCP 超时就会落到用户手动重连。
2. 列表刷新和首页使用独立 Session；进入首页会取消列表刷新。`PlatformPinnedHttpClient` 用全局递增序号生成请求 ID，每个实例仅取消自己的 pending 集合；原生 `PinnedHttpsCalls.cancel` 按 ID 找 Call。现有代码和本次日志未发现旧页面取消新页面 TCP 请求的证据。
3. 发现流程会检查其他主机的候选地址。日志中请求 RK3588 身份却访问 `.37` / `.32` 后出现 TLS 不匹配，是候选筛选被正确拒绝；随后仍尝试 `.33`。它不表示 RK3588 的身份或手机授权变化。
4. `HostLocationException` 继承 `LocalApiRequestException`，Controller 会保留“已发现局域网服务，但连接超时”的说明。诊断测试排除了“错误被通用 catch 吞掉”的假设。
5. 可读名称变更只影响显示值，连接仍使用原 Host ID、密钥及地址；未发现名称修改进入连接地址或身份匹配逻辑。

相关实现：

- `lib/src/features/host_setup/host_product_session.dart`：首次连接、候选验证、认证及失败分类。
- `lib/src/features/host_setup/host_locator.dart`：地址来源、去重与候选竞争。
- `lib/src/features/setup/eidolon_app_shell.dart`：列表刷新取消与页面进入。
- `lib/src/features/host_setup/pinned_http_client.dart`、Android `PinnedHttpsCalls.kt` / `PinnedHttpsProtocol.kt`：请求所有权、取消和超时。

## 修复设计

在现有共享连接层，为首次连接的只读 Host 身份探测增加最多一次的短暂传输故障重试，成功后再走原有认证。复用原候选、超时及取消机制；继续验证原 TLS pin 和 Host 身份。目标是让本来需要用户再点一次的短暂故障有一次自动恢复机会，不能保证消除持续性网络故障。

- 只对超时、暂时不可达等明确的传输失败生效。
- TLS/Host 身份不匹配、格式不兼容和管理授权被拒绝，不靠重试掩盖。
- 页面退出、Session 关闭、网络变更后，旧尝试必须结束或交给现有网络 revision 处理。
- 不通过通用 HTTP 自动重试重放认证或其他写请求；不扩大 BLE 自动访问范围。
- 失败提示保留目前正确的超时说明；增加诊断时只记录目标、阶段、尝试次数与耗时，不记录凭据。

增加回归覆盖：首次探测超时后成功；两次失败后结束；重试等待中离页；切换 A/B 主机时旧取消不影响新请求；身份拒绝不重试；认证写请求不重复。

## 本轮验证

- 连接、列表观察、网络变更、页面离开及请求取消相关现有测试共 66 项通过。
- 两项临时诊断测试验证：同一地址第一次只读探测超时会直接失败，显式第二次连接成功；Controller 正确保留超时说明。
- 诊断测试只用于确认当前行为，已从仓库工作区移出，避免把“必须手动重连”固化为未来实现要求。
- 平板日志保存在本机临时目录，未将含其他应用信息的整份 logcat 加入仓库。

## 修复实施

- 在 `HostProductSession._connectOnce` 原有候选验证与认证之间加入一次有限恢复：只有当前候选组没有成功地址时，筛出超时、不可达、I/O 传输失败的地址，再通过原 `_firstToAnswer` 探测一次。
- 同一轮定位的 URL 去重仍然保留，因此每个地址最多探测两次；已有其他候选成功时直接继续认证，不重试失败地址。认证和后续业务调用位于重试范围之外。
- 两轮探测均执行原 TLS pin 和 Host 身份验证，复用原请求取消机制；重试前后校验网络 revision 和 Session 开放状态。没有引入新缓存、连接管理器或后台任务。
- 重试期间显示“连接暂时未完成，正在重试”。原有 8 秒请求超时不变；持续离线时，一个超时候选最多多等待一次 8 秒请求预算，随后继续原回退或报告失败。不会无限重试，也不承诺修复底层网络不通。
- 新增 15 项回归用例，覆盖短暂传输失败后成功、两次失败终止、身份/格式/授权拒绝、取消不重试、认证 POST 不重复、离页释放及新旧 Session 隔离、网络变更丢弃旧目标。

### 修复验证与剩余问题

- 全量 Flutter 测试：976 项通过、5 项跳过；静态分析无问题，Debug APK 构建成功。
- 已通过 `adb install -r` 安装到平板 `df331f93`，保留应用数据。Mac 页面安全连接并成功读取概览；切回 RK3588 后实测了有限失败路径。
- 真机 RK3588 首次探测约在 16:32:58 超时，第二次约在 16:33:06 超时，页面随后显示连接超时及“重新连接”，未继续第三次探测。原生日志的 `cancelled` 包含 Dart 请求期限到达后的主动取消，不能把所有此类记录解释为页面退出。
- 该实测确认两次探测上限和错误反馈正常，但没有证明 RK3588 的底层 TCP 建连故障已消失。短暂失败后自动恢复由可控回归测试验证；连续超时仍需要后续结合主机侧或链路证据排查。本次提交只修复客户端缺少有限恢复的问题。
- 同期从平板执行 `ping -c 3 -W 1 192.168.1.33`，3 个探测均未收到响应。这是额外的链路观测，仍不能单独区分网络丢包、主机状态或 ICMP 策略。
