# 主机连接与设备接入：架构简化方案

状态：Mobile 架构修复已实施，自动化回归及当前网络下 Pi5 页面验收已完成；另一任务已验证 BOX-3 正常配网与自动接入，实际语音演示和热点实测未完成。基于 `369aec7`，合并保留同工作区的设备配网阶段文案修改。实施证据见文末。

## 1. 保留什么，简化什么

`owner_domain_generation` 是 Owner 授权状态重建后的失效边界，不是主机型号、软件版本或连接次数。现有 Ops 的 Authority lineage 决策及测试规定：授权状态保留时不推进 generation；授权状态被清空并重建时推进，阻止旧授权材料与新空状态混用。

保留这一个协议字段及 Authority 的最终验证，不在页面上显示“第几代”，也不新增替代它的 session epoch、scope version 等同义机制。简单删除它会让旧签名授权和重置后的状态难以区分，或迫使系统通过更换整个 Owner 身份实现相同效果；并不会减少实际恢复复杂度。

需要简化的是分散的判断、历史任务自动接管页面、重复的事实来源。手机检查点表示“这台手机上一次做到了哪一步”，不能充当“设备当前是否获授权”的权威状态。

本次 Pi5 已确认旧检查点 generation=8、当前 Authority=9，但尚未取得触发 8→9 的具体操作证据。实施时须复核部署/重置记录：如果普通升级意外销毁 Authority 数据，应修复部署生命周期，不能仅通过手机失效旧记录掩盖。

## 2. 设备接入：现有 Coordinator 统一负责恢复资格

### 模块职责

| 现有模块 | 收敛后的职责 |
| --- | --- |
| `DeviceSetupPage` | 承接“添加新设备”或用户选定的“继续接入”，渲染进度和可执行动作 |
| `DeviceSetupCoordinator` | 统一判断检查点是否属于当前授权状态、是否还能恢复；执行原有接入流程 |
| `DeviceSetupCheckpointStore` | 保留原幂等操作 ID、设备侧已完成步骤等恢复材料，继续使用原存储格式 |
| `DeviceAdmissionPort` / Hub | 返回当前 Enrollment / Claim 事实、做最终授权校验；不由手机猜测 |

不新增 RecoveryManager、任务数据库或平行状态机。恢复资格是由已有字段计算出的结果，不再持久化一份“可恢复状态”。新发起复用、自动发现可继续任务、按 setupId 显式恢复都调用同一规则，避免只在 UI 补一个 if。

统一规则：Owner ID 和 generation 匹配；物理配置阶段满足恢复条件；不是已完成、拒绝、取消、撤销、过期或不可重试失败。由已有状态及 Authority Projection 归类，保留未知/暂不可用与终态的区别。

### 用户流程

- “添加设备”始终进入新设备准备/扫描流程。页面可同时提示有进行中的接入，并提供“继续接入”；多个任务由用户选择，不按更新时间偷偷选择一个。
- 当前明确选择的进行中任务，允许断网重试、应用返回后的自动观察与崩溃恢复；保留既有幂等 ID，不重复写入网络或批准。
- 旧授权状态、已终结任务退出可恢复列表，不向当前 Authority 反复发送旧请求，不清空其他 Owner 或有效任务的记录。
- 有效恢复请求最终返回 404 时，将该任务按契约终结，保持新设备入口可用；不把 404 当网络错误重试，也不自动给设备重新授权。
- UI 只说明“上次接入已失效，可以重新添加”等结果；Enrollment、Grant、generation、HTTP code 留在技术详情。

### 不在本轮混合迁移

检查点现有 wire 字段、签名链、Voucher/Decision/Grant/ack 契约及 ESP32 协议保持兼容。本轮先删除重复选择与判断路径；不把存储压缩、协议合并和 UI 修复捆绑成跨端大迁移。

## 3. 主机连接：一个定位入口，已知地址先开始验证

仍由 `HostLocator` 产生候选、`HostProductSession` 验证身份并认证、`HostProductController` 为页面提供状态。复用现有候选竞争与取消机制，不新建 ConnectionManager 或常驻多主机会话池。

- 选中已保存主机后立即验证已知地址；发现作为失败后的回退或有上限的延迟并行分支。实现上让现有 Locator 与候选调度协同，不能简单交换两个串行来源、先等旧 IP 超时两次再扫描。
- 新地址一旦通过同样的 TLS pin 与 Host 身份校验，即可胜出；释放其他尝试。只在选定地址后执行一次认证写请求。
- 各次进入共用相同定位策略；列表读取仍有明确生命周期，离开列表取消它的请求，不让列表刷新占用首页的连接预算。
- 同一首页及子页面沿用现有 Controller/Session；并发准备继续合并为同一个 Future。离开首页释放会话，网络变化丢弃旧候选。
- 页面主要显示“正在连接”“连接超时”，仅在确实需要地址恢复时说明“正在重新定位地址”；列表中的可达性保留验证时间，不能把历史状态当作当前保证。
- 已有有限重试纳入同一个尝试预算：成功替代地址优先于重复失败地址，不在页面、Controller 和 HTTP 层叠加自动重试，不扩大 BLE 自动访问范围。

这个改动处理反复等待完整发现的体验问题，不能修复 RK3588 的无线信标丢失。

## 4. RK3588：在 Host foundation 层解决无线问题

已确认 Broadcom DHD 反复报告 beacon loss，导致无线掉线。单次关闭省电未消除故障；目前不能直接指定某个配置或固件为已验证修复。

- 使用独立有线/串口管理，保证观测不会随无线掉线中断。
- 单变量对照 AP/频段、受支持驱动固件及无线设置，记录关联断开次数、丢包、延迟与 TCP 成功率。必要时对照外置网卡以区分板载链路问题。
- 验证有效后，通过现有 Ops/foundation 的硬件 profile 和部署机制固定依赖与配置，并具备回退。硬件/天线或 AP 问题则处理对应部件/配置。
- 不由手机远程反复重启 Wi-Fi，不新增 watchdog 补偿，不把“延长超时”或“切 IPv6”当作无线链路修复。

## 5. 实施顺序与回归门槛

1. 先修设备接入职责与恢复资格，解除 Pi5 的确定性逻辑故障；同步复核 Authority generation 变更的部署来源。
2. 调整现有定位/候选调度，优化主机切换延迟；保持安全验证、取消和认证边界。
3. 无线独立对照完成后再落 Host foundation 变更；不因手机测试通过就宣称驱动问题解决。

必测：新设备入口不被旧任务占据；generation 相同的有效任务正常恢复；generation 不同或终态不自动恢复；恢复中 Authority 更新能终止旧操作；回复丢失不重复批准/配网；其他 Owner 数据保留；已知 IP 可用时不等待发现；旧 IP 失效时发现不被长超时串行阻挡；新旧候选互不误取消；跨 Host 身份校验不放宽。

无线验收需额外做持续链路观测和真机多轮切换，明确记录 AP、频段、驱动/固件与实验时长；短时一次连接成功不能作为通过依据。


## 6. 2026-09-10 实施与交付记录

### 已落地

- `DeviceSetupCoordinator` 使用同一 `belongsTo / canResume` 规则筛选恢复任务和约束既有流程复用；通过现有 `loadTarget` 回调读取当前 Authority，不建立第二套授权缓存。恢复前、持续查找 Enrollment 时、提交 Decision 前检查授权边界。
- `DeviceSetupPage` 进入时只列出可继续任务，不自动选最新历史；新设备入口始终保留。只有明确选中的任务进行前台观察，完成/拒绝/失效停止观察；使用另一 Owner 的入口不能修改原任务。
- 保留检查点 wire 格式、已有操作 ID、两次设备 AP 访问的先后次序、原有幂等审批和 Claim 完成判据；没有清空平板存储或重置 Pi5 授权。
- `HostLocator.locateNetwork` 独立收集网络来源；`raceHostAddresses` 支持候选陆续到达，仍沿用 250ms 错开探测和胜出后释放其他尝试。已知 IP 不等发现结束，旧 IP 不挡新地址。
- `HostProductSession` 使用原有会话请求所有权来取消候选竞争，网络改变时立即取消旧发现订阅；继续保留 TLS/Host 身份验证、一次有限只读重试、BLE 显式回退和单次认证边界。列表与首页沿用这一套 Session 策略。
