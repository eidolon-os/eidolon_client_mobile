# 设备配网后接入等待：Owner 路由修复

## 现场证据

2026-09-10 的原始现场时间线：Mobile 于 16:44:27 收到并确认设备的配网提交终态；Pi5 在 16:47:51 收到 Enrollment，16:47:52 收到来自平板 `192.168.1.21` 的 Local API 审批请求；设备随后领取并确认 Grant，Mobile 于 16:48:03 保存 `claimActive` 并显示完成。

本任务此前只读取现场状态，没有通过调试工具提交审批或修改检查点。审批由 Mobile 按用户“确认配网并批准这次设备接入”的既有流程发送。

原始现场没有同时采集 ESP32 串口，因此不能仅凭上述时间线认定三分多钟全部花在 mDNS。代码审查与隔离复现确认了一个能阻塞登记的缺陷：固件先做通用 mDNS 发现，按广播顺序取候选，然后才检查 Owner。即使目标 Pi5 同时存在，OPi5 排在前面仍会被选中并拒绝，进入 10/20/40/80/120 秒退避。现场网络同时广播两个 Owner。

## 修复

- ESP32 首次接入与运行中重连统一由 `HubOnboardingClient::Run` 读取已验证的 Owner 目录，先访问其签名目录地址。
- 只有直接路径失败才回退到发现；发现必须显式传入 Owner ID，并跳过其他 Owner。发现结果仍经原有证书、签名、代际、目录修订校验。
- 新配网或 Owner 代际变化使操作失效时，不再开始发现回退。
- Mobile 从配网检查点明确呈现“Wi-Fi 已配置，正在接入主机”，分别显示等待登记、批准、凭据交付和完成；不把 Wi-Fi 成功当成 Claim 成功。
- 登记等待超时提示明确说明无需重新配网，保持原有自动恢复与幂等审批流程。
- 确认表单明确说明会再次连接设备发送 Wi-Fi，以及第二次 Android 系统连接授权需要点击“连接”。现有 SoftAP 两次访问仍保留：读取身份后释放设备网络、访问主机领取凭证，然后重新连接设备发送配置。

## 烧录时发现的额外启动问题

使用 `scripts/eidolon/eidolon-esp-box-3.sh` 首次烧录后，串口发现显示库初始化崩溃。回溯为 `gfx_log_writev → printf → nano-vfprintf`：保存的 BOX-3 sdkconfig 启用了不支持 64 位整数的 nano 格式化，但显示库日志使用 `PRIi64` 时间戳。默认配置不会覆盖已保存的 sdkconfig。

BOX-3 正式构建脚本现强制关闭 `LIBC_NEWLIB_NANO_FORMAT` 及旧别名，保留第三方库原样。构建指纹匹配本身不能证明启动成功，必须结合后续串口启动与接入结果验收。
